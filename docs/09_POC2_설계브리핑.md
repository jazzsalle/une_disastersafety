# 09. POC2 설계 브리핑 팩 (ChatGPT 설계 작업 입력용)

> 이 문서는 재난안전 AI 시범 서비스 **POC1의 전체 현황을 저장소 접근 없이 파악**할 수 있게 압축한 브리핑이다.
> POC2 기획(실시간 관측 API 연동, T3Q 규격 정합, 지자체·재난유형 확대)의 입력 자료로 작성됐다.
> 첨부한 다른 문서와 내용이 다르면 **이 브리핑이 최신·우선**이다(§F-2 문서-구현 격차 참조).
> 내부 공유용 문서다 — T3Q 사이트 정보가 포함되므로 외부 반출 금지.

## A. 사업·POC1 개요

- **사업**: NIA 「재난안전 AI데이터 구축」(티쓰리큐 컨소시엄). 역할 분담 — T3Q: 플랫폼(EDPP)·데이터 파이프라인·RAG/VectorDB·LLM / 아이타이쿤: 재난메타·온톨로지 스키마 검증 / **유엔이(우리): AI Agent 실증 서비스·시각화 화면**. 본 저장소는 유엔이 담당분의 선행 POC.
- **POC1 범위**: 지자체 3종(의왕 41430·구미 47190·남원 45190 — 본사업 목표는 부산/인제/영천), 재난 5종(호우 HEAVY_RAIN·T10107 / 홍수 FLOOD·T10206 / 수해·침수 INUNDATION·T10106 / 태풍 TYPHOON·T10105 / 산사태 LANDSLIDE·T10401), 문서 6종(의왕·구미·남원 자연재해저감종합계획 + 요천·구미천·안양천 하천기본계획) 5,745쪽 → **근거 단위(passage) 3,974건**.
- **핵심 원칙**: 모든 AI 응답에 출처(문서명·장·페이지) 필수 — 근거 없는 답변 금지(XAI). 식별자 5단 체인 `source_asset_id → evidence_unit_id → passage_id → event_id → rag_answer_id`.

**화면 모듈 6종** (3열 대시보드: 좌 300px 입력 / 중앙 지도+질의응답 / 우 400px 탭, 라이트·다크):
| 모듈 | 요지 |
|---|---|
| ①상황입력 | 재난유형 칩 5종(T코드 병기)·경보종류/단계·일시·피해 칩·메모 → 「적용」 시 event_id 발급 + 구조화 질의 JSON. 유형 선택 시 판단기준 탭 자동 전환 |
| ②지도 | VWorld 2D 타일+Leaflet. L1 위험지구 마커(29) / L2 하천구간 면형(계획홍수량 팝업) / L3 행정경계 / L4 위치미상 목록 폴백. Top-K 카드↔마커 연동 |
| ③유사사례 Top-K | 카드(유형 배지·유사도%·요약·출처)+정렬·필터, 클릭 시 상세+지도 연동 |
| ④상세조회 | 위험지구(등급·예상피해액·저감대책·사업비·근거 p.x) / 하천(산정지점 표: 계획홍수량·홍수위·특보 기준유량 50/70%, 안양천은 2015/2020 병기) |
| ⑤정합성 | 근거응답: 답변+Citation 목록(문서·장·쪽·인용, 클릭 시 원문 표 플로팅 창)+요인 기여도 바 |
| ⑥챗봇 | 질문 칩 6종, POI 자동 첨부, 응답 내 지명 클릭→지도 이동, 「정형 데이터 즉답」/「mock」 배지 |

**시연 스토리(docs/07, 5분)**: "남원에 시간당 60mm, 특보 발표 전" — 1막 상황 등록(판단기준이 60mm를 주의보 3h 60mm·극한호우 1h 50mm 기준으로 판정) → 2막 챗봇 칩 6종(기준유량 즉답, "유량 1100 주의보?" 1건만 LLM 실연동) → 3막 근거응답 Citation 원문 확인 + 유사사례. 시연 중 타이핑 없음.

**스택·배포**: 검색 rank-bm25(+kiwipiepy) / 근거응답 Claude `claude-sonnet-5`(키 없으면 결정적 mock) / 챗봇 UNI RAG(사내 LLM 서버) SSE 프록시(실패 시 mock) / FastAPI / React18+Vite(UNE 디자인시스템) / Vercel(서울 icn1, Python 서버리스, 데이터 5종 번들) / 외부 공개용 `public-demo` 브랜치 별도(로그인·UNI 연동 제거판).

## B. 유지해야 할 계약 (POC2가 깨면 안 되는 것)

**API 표면 (전수, prefix `/api`)**:
`GET /health`, `POST /auth/login·logout`, `GET /auth/me`, `GET /meta/hazards`, `GET /meta/regions`, `GET /criteria`, `GET /criteria/{code}`, `GET /districts?admin=&hazard=&kind=`, `GET /rivers?admin=`, `GET /geo?admin=&layer=`, `POST /search`, `POST /cases/search`, `POST /ask`, `POST /chat`

**핵심 4종 요청·응답**:
- `POST /search`: 요청 `{event, query, top_k(1~20)}` → `{results[{passage, score, similarity_factors, source}], filter_relaxed}`. `similarity_factors` = type(유형 교집합)·space(행정코드 일치)·damage(키워드 매칭)·**time(0.5 고정 — 계획문서에 사건 시점이 없다는 POC1 한계, POC2 실시간 연동의 개선 대상)**. 점수는 BM25 × (1+Σw·factor).
- `POST /ask`: → `{rag_answer_id("RAG-{ts}-{uuid8}"), answer, mode("claude"|"mock"), no_evidence, top_k_results, citations[{passage_id, doc_title, chapter, page_start, page_end, quote, tables}], structured_refs{districts,rivers,criteria}, geo_refs(FeatureCollection, L1~L3)}`. 근거 없으면 `no_evidence=true`(자유 생성 금지).
- `POST /cases/search`: `{event, top_k, scope: local_first|local|basin|national}` → 사례 카드(지구 단위, region_relation "관내/동일 유역/타 지역").
- `POST /chat`: `{query, history[], event, poi}` → 성공 시 SSE 스트림(`X-Chat-Mode: uni_rag`, 첫 이벤트로 로컬 발췌 `__local_excerpts__` 전송), 실패 시 JSON mock 폴백(`X-Chat-Mode: mock`).

**아키텍처 원칙**: LLM·검색·챗봇 호출은 `services/` 어댑터 3종(llm.py·retrieval.py·uni_rag.py)에만 격리 — **T3Q RAG API/AI Agent 규격이 확정되면 어댑터만 교체하고 라우터·프론트 계약은 불변**. POC2 설계도 이 원칙을 유지할 것.

**챗봇 3단 캐스케이드** (확장 시 이 위에 얹을 것): ①지도 명령 파서(동사+대상 동시 존재 시, LLM 미호출) → ②정형 데이터 즉답(기준유량·수위계·저감대책·선정이유·피해이력 5종 정규식 → JSON 직조회, 0초 응답·출처 병기) → ③"판단·발령"류 질문만 LLM(UNI RAG)으로 — 백엔드가 POI 기준유량 표·판단기준·상황을 컨텍스트로 자동 주입.

## C. 데이터 자산

**판단기준 5종 (criteria.json — 전 항목에 Q1 정량조건·Q2 등급체계·법적 근거·출처)**:
| 유형 | 판단주체 | Q1 정량 기준 |
|---|---|---|
| 호우 | 기상청 | 주의보 3h≥60 또는 12h≥110mm / 경보 3h≥90 또는 12h≥180mm / 극한호우 문자 1h≥50 AND 3h≥90 (또는 1h≥72) |
| 홍수 | 환경부 홍수통제소 | 주의보 = 계획홍수량 50% 유량 수위 초과 예상 / 경보 = 70% (특보지점 223곳) |
| 수해/침수 | 행안부 | 단일 정량기준 없음(no_single_criterion) — 구성재해 특보 준용 + 피해 발생 |
| 태풍 | 기상청 | 중심최대풍속 ≥17m/s, 강도 5단계(17/25/33/44/54m/s), 경보: 강풍 21m/s·총강우 200mm 등 |
| 산사태 | 산림청 | 토양함수지수 80% 주의보 / 90% 예비경보 / 100% 경보 |
공통: 재난 위기경보 4단계 관심(Blue)→주의(Yellow)→경계(Orange)→심각(Red).

**하천 (rivers.json, 3하천)**: 하천별 개요(유역면적·연장·설계빈도·계획명)+산정지점 배열. 특보 기준유량은 `계획홍수량×0.5(주의보)/×0.7(경보)` **산출값(고시값 아님)** 명기. 예: 요천 Y4 남원수위표(No.15+290) 계획홍수량 2,005㎥/s → 주의보 1,003 / 경보 1,404. 지점마다 evidence(문서·장-쪽 "3-80"·표 번호·PDF쪽). 안양천은 기수립 2015(270㎥/s)/금회 2020(315㎥/s) plan_version 이중 수치. `warning_reference_station`(참조 수위표) 필드 보유.

**위험지구 (districts.json, 29개소)**: 필드 29종 — 재해유형(8종 구분)·hazard_codes(T코드)·위치·하천·**risk_thresholds[]**(대상·연산자·값·단위·근거표)·등급·저감대책·사업비·예상피해액·**damage_events[]**(발생일·명칭·설명·출처 페이지)·우선순위·좌표(VWorld 지오코딩 완료). 예: 의왕 안양천지구 제방여유고 2.96m 부족, 사업비 26,513백만원, 우선순위 1/17.

**지도 (geo.json)**: L1 위험지구 Point 29 / L2 하천구간 MultiPolygon 3(VWorld 하천망 실형상) / L3 행정경계 3(VWorld 실경계) / L4 0건(위치미상 목록 폴백 설계만). EPSG:4326.

**코퍼스 (chunks.jsonl, 3,974건)**: 22필드 — passage_id·evidence_unit_id·source_asset_id·문서/발행처·admin_code·hazard_codes(T코드)·disaster_kind(저감계획 8종 재해구분)·river_name·chapter/section·page_start/end·본문·tables(표 원문)·page_label("장-쪽" 체계). 청킹: 장·절 경계 우선 → 위험지구 1건=1청크 → 800~1,500자 슬라이딩.

**알려진 데이터 한계**: 구미천 유역 실측 수위관측소 없음 / 구미천 GM01·03·07 계획홍수량은 구간 배분값 / 남원 행정코드 45190이 VWorld에서 NOT_FOUND(전북특별자치도 개편 52190 폴백) / 남원 부록 HWP·안양천 스캔 페이지 미추출.

## D. 주관기관(T3Q) 구축 방향 요약 — 상세는 첨부 docs/08

2026-07-30 T3Q 데이터 구축 테스트 사이트를 조회 전용으로 분석한 결과(테스트 모듈이며 확정 규격 아님):
- **파이프라인**: 원시 → 문제유형정의(스키마 수집·문서 md 변환·응용온톨로지 생성) → **Passage 인스턴스 구축**. 모든 데이터(정형 DB 포함)가 SchemaType별 Passage로 수렴하는 RAG 전제 설계.
- **허브 온톨로지**: DisasterEventMasterPassage(사건 Master) + 도메인 스키마 45종이 `RefDisasterEventID`로 역참조. **EVENT_ID = `{YYYYMMDD}-{유형코드}-{행정5자리}-{순번3}`** (예 `EVT::20240715-FLOOD-44210-001`) — POC1의 `[유형]-[일자]-[행정5]-[순번4]`와 요소 동일, 순서·자릿수만 상이.
- **표준 코드 9종**: disaster_type(간이: FLOOD·TYPH·SLOPE…), crisis_level(LVL_01~04 = 관심/주의/경계/심각, POC1과 동일), damage_scale(DMG_*), risk_factor(rain_fall·river_level·slope…), **observation_source(MET_AWS·MET_ASOS·SAT_SAR·SAT_OPT·GIS_ADM·GIS_HAZ·GIS_VULN)**, sop_stage, doc_type, propagation_channel, ai_analysis_type(**AI_SIM=유사사례** 포함).
- **T코드 택사노미**: TTAK.KO-10.1047 기반 3단 77노드(T10105 태풍·T10106 풍수해·T10107 호우·T10206 홍수·T10401 산사태 등)가 온톨로지에 공식 탑재, prefix 필터 — POC1 hazard_codes와 같은 표준. 사건 속성에는 간이 코드, 분류에는 T코드의 **이중 체계**.
- **재난유형 코드 매핑(필요)**: HEAVY_RAIN↔TYPH(태풍·호우)/T10107, FLOOD↔FLOOD/T10206, INUNDATION↔FLOOD(T3Q FLOOD가 "홍수·침수" 포괄 — 우리가 더 세분)/T10106, TYPHOON↔TYPH/T10105, LANDSLIDE↔SLOPE/T10401.
- **근거 계보**: 정형 DB(전국 위험지구 14,921건 — 저감계획 시도 입력 DB 원천) 각 행에 원본 엑셀 경로·시트·행 lineage 부착. POC1 evidence 체인과 동일 철학.
- **홍수취약지구 관리카드**(인스턴스 구축 최선행, 249건): RiverPlan(측점·계획홍수량·계획홍수위·제방고) + **FloodRiskSystem(대응수위·참조관측소·단계별 제공수위: 1단계 주의보/2단계 경보·SMS/CBS)** — POC1 rivers.json과 동일 도메인. POC2 하천 화면 필드 정렬 대상.
- **역량질의(CQ) 5문**: ①어떤 하천이 범람 위험 ②저지대 침수 위험 지역 ③산사태 위험 지역 ④모니터링할 수위계/우량계 ⑤과거 침수지역 — POC1 챗봇 칩·시나리오와 사실상 동일 구조.
- **원시 커버리지**: 소하천정비종합계획 전국 적재(의왕·구미·인제·영천 있음 / 남원·부산 없음), 저감계획·하천기본계획 **비정형 본문은 미착수(0건)** — POC1 코퍼스와 상호보완. 대외 MCP/RAG API는 미노출(내부 변환 Agent 단계).

## E. POC2 확장 3축 — 설계 입력

### E-1. 실시간 관측 API 연동 (기존 문서상 "확장 1순위")
POC1은 실황 미연동(담당자가 관측값을 상황입력에 수동 등록). DESIGN.md 고도화 메모: "판단기준 게이지에 실황 주입".

| 재난유형 | 판단기준 변수 | 후보 API | 판정 로직(이미 데이터 보유) |
|---|---|---|---|
| 호우 | 1h/3h/12h 강우 | 기상청 API허브(apihub.kma.go.kr)·기상자료개방포털 AWS/ASOS 실황 | criteria의 3h60/12h110·1h50 기준과 즉시 비교 판정 |
| 홍수 | 하천 수위·유량 | 한강홍수통제소(hrfco.go.kr) 수위/유량 OpenAPI, WAMIS | 관측값 vs 계획홍수량 50%/70%(rivers.json 산정지점별 기준유량 표) |
| 산사태 | 토양함수지수 | 산림청 산사태정보시스템 | 80/90/100% 3단계 판정 |
| 태풍 | 풍속·강우·해일 | 기상청 태풍정보·특보 API | 17/21m/s·강도 5단계 |
| 공통 | 특보·재난문자 | 기상청 특보 API, 긴급재난문자 CBS(공공데이터포털) | 상황입력 "경보종류·단계" 자동 채움 |
보조: RIMGIS 하천관리지리정보 WFS(하천망 정밀화), NDMS(본사업 연계 시).

설계 포인트:
- **주입 지점 2안**: (a) 상황입력 패널 자동 채움 — 지자체 선택 시 실황 강우·수위·특보를 폼에 프리필 (b) 판단기준 탭 게이지 — 기준 대비 현재값 게이지 표시(예: Y4 관측유량 1,100 → 주의보 1,003 초과 표시). 두 안 병행 가능.
- **관측소-하천 매핑 데이터 신설 필요**: rivers.json에 `warning_reference_station`(남원수위표) 필드가 이미 있음 → T3Q FloodRiskSystem의 "참조관측소(관측소명·대응수위·거리)" 구조로 확장하면 정합. 관측소 ID↔산정지점↔지구 매핑 테이블이 POC2의 신규 데이터 자산.
- **similarity_factors.time=0.5 고정 해소 기회**: 실황·사건 시간축이 생기면 time 요인을 실제 값으로.
- 유의: 구미천은 유역 내 실측 관측소가 없음(대체 지점·추정 방식 설계 필요). 특보지점 223곳 중 POC 하천 포함 여부 확인 필요.

### E-2. T3Q 규격 정합(선반영)
- event_id 생성기를 T3Q 형식(`{YYYYMMDD}-{TYPE}-{REGION5}-{SEQ3}`, `EVT::` 접두) 겸용으로 — 변환 함수 1개로 호환.
- 재난유형 코드 매핑표(§D)를 meta 데이터로 보유, API·챗봇이 양쪽 코드 수용.
- T코드 필터(3단 prefix) 유지·강화 — T3Q 택사노미와 동일 규칙.
- 하천 상세·데이터 필드를 FloodRiskSystem 용어와 정렬(참조관측소·단계별 제공수위). E-1 관측소 매핑과 동일 작업.
- 실시간 연동 시 관측원 표기를 T3Q observation_source 코드(MET_AWS 등)로 채택.
- Passage·lineage 용어는 이미 정합 — 유지.

### E-3. 지자체·재난유형 확대
- 구조: 문서(PDF/HWP) 투입 → 파이프라인 재실행만으로 지자체 추가되는 설계(POC1 검증됨). 확대 시 수동 검수 시드(criteria는 공통, districts·rivers·geo는 지자체별 추가)가 병목 — 자동화 수준이 설계 쟁점.
- 본사업 목표 부산/인제/영천: T3Q 원시 코퍼스에 인제·영천 소하천정비종합계획은 이미 있음(부산 없음) — 문서 수급 경로로 활용 가능성.
- 함정: 행정코드 개편(남원 45190→52190류), 하천기본계획 문서 식별·수급(river.go.kr 고시목록), 계획 버전 혼재(plan_version 필수), HWP·스캔 문서 비율.

### E-4. ChatGPT가 설계에서 결정해줘야 할 질문
1. 실황 주입 지점: 상황입력 프리필 vs 판단기준 게이지 vs 병행? 화면 우선순위는?
2. 갱신 주기·방식: 폴링 주기(10분?), 서버 캐시 vs 클라이언트 직호출, Vercel 서버리스(최대 300s) 제약 하 스케줄링?
3. API 키·쿼터 관리: 공공 API 키 4~5종의 보관(.env)·쿼터 초과 시 동작?
4. 오프라인·시연 안전망: API 장애 시 mock 실황(결정적 시나리오값) 폴백 설계 — POC1의 mock 폴백 패턴 준용?
5. 실황 vs 계획수치 병기 UI: 혼동 방지 표기(관측값/기준값/산출값 구분 배지)?
6. 확대 지자체 우선순위와 문서 수급 계획(부산 소하천 자료 부재 대응)?
7. event_id를 T3Q 형식으로 전환할 시점(POC2부터 vs 어댑터 변환만)?
8. 시연 시나리오 개정: "특보 발표 전 60mm" 스토리에 실황 게이지가 들어가면 1~2막이 어떻게 바뀌나?
